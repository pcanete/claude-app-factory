# Evolve an application's schema

An application generated by Claude App Factory has its structure compiled from `app-spec.json`.
Changing it is not editing files: it is producing a new AppSpec, planning the change, and letting
the factory write the next migration.

**The trap this skill exists to prevent:** regenerating the application and copying everything over
it. That rewrites `database/generated/001_initial.sql`, whose checksum is already recorded in the
`app_migration` ledger, and the next deploy dies with *"La migración aplicada fue modificada"*.
Never copy a regenerated `001`.

## What you need first

Establish three paths before anything else, asking only for what you cannot determine:

| What | How to find it |
|---|---|
| The application | The directory holding `app-spec.json` and `database/generated/` |
| The factory | The clone of `claude-app-factory`, which has `scripts/evolve_app.py` |
| The database | `DATABASE_URL` or `POSTGRES_URL` in the application's `.env.local`, or pulled from the deployment |

If the application has no `app-spec.json`, it was not generated by this factory. Stop and say so.

## Procedure

### 1. Snapshot before touching anything

```bash
git -C <app> status --short
```

Uncommitted work means the change cannot be rolled back cleanly. Commit or stash first — do not
proceed over a dirty tree.

### 2. Write the proposed AppSpec as a separate file

Read the current `app-spec.json`. It is the **database contract baseline**: never edit it in place
and never overwrite it before the plan is reviewed.

Translate the request into a copy, at `<app>/../proposed.app-spec.json` or a scratch path. Keep every
existing key, field order and identifier untouched — a diff should show only the intended change.

Rules that matter when writing it:

- keys are `snake_case`, matching `^[a-z][a-z0-9_]*$`; labels are human-facing and may carry accents;
- a new required field needs a `default`, or the change will be blocked;
- a new `belongs_to` on an entity that already has rows must be optional;
- enum options can be added, never removed;
- entity names come from the client's own domain, never from a CRM vocabulary;
- if the request implies a role that administers users, give it `capabilities: ["manage_users", …]`.

### 3. Plan, and read the plan

```bash
python <factory>/scripts/evolve_app.py --project <app> --spec <proposed.app-spec.json>
```

The report lists changes, warnings and blocked operations. **Read all three sections aloud to the
user before doing anything else.** A blocked plan exits with code 3 and writes nothing.

If something is blocked — removing or renaming a field, changing a type, dropping an enum value,
making an existing field required — do not look for a flag to force it. There isn't one, and that is
deliberate. Explain what the operation would do to the rows that already exist, and what a reviewed
migration would need: a backfill, a backup, and a rollback plan. That is a separate conversation, not
this procedure.

### 4. Apply only a clean plan

```bash
python <factory>/scripts/evolve_app.py --project <app> --spec <proposed.app-spec.json> \
  --migration-name <short_snake_case_name> --apply
```

This writes `database/generated/NNN_<name>.sql`, refreshes `app-spec.json`, `src/generated/` and the
reports, and touches nothing that belongs to the client. Read the generated migration before running
it against any database.

### 5. Migrate, then verify — in that order

```bash
cd <app> && pnpm db:apply && pnpm typecheck && pnpm db:smoke
```

`db:apply` skips migrations whose checksum already matches and applies only the new one. If it
complains that an applied migration was modified, something copied a regenerated `001`: restore it
from git instead of editing the ledger.

Prefer a scratch or preview database for the first run. Never let production be the first place a
migration executes if any alternative exists.

### 6. Ship and confirm

Commit the AppSpec, the generated files and the new migration together — they are one change. Then
deploy, and confirm against the running application rather than against the build log:

- the new field appears on the record form and on the entity's table view;
- an existing record still opens and still shows its previous values;
- a role that should not see the new entity gets `/forbidden` when entering by URL;
- if the change touched rules, the rule fires.

A green build is not verification. This is not a slogan: a deploy of this very application
reported `READY` while `/api/health` answered `503`, because an environment variable pointed at a
file that does not exist in the serverless runtime. Only hitting the running application caught it.

## Never

- Edit `app-spec.json` in place before the plan is reviewed.
- Copy a regenerated `database/generated/001_initial.sql` over the existing one.
- Edit an applied migration, or rewrite a row in `app_migration` to make a mismatch go away.
- Force a blocked operation.
- Add behavior the AppSpec cannot express — calculations, integrations, bespoke screens. Those are
  features under `src/features/`, and they do not belong in a schema change.
- Touch `src/platform/` or `database/platform/`: the factory owns and updates those.

## When the answer is not a schema change

Some requests sound structural and are not:

| Request | Where it actually belongs |
|---|---|
| "each person should only see their own records" | a client feature; permissions are per role and entity |
| "calculate the total automatically" | a client feature, or a deterministic AppSpec rule if it is a plain assignment |
| "send an email when this changes" | a client feature; AppSpec rules have no side effects |
| "let the client add fields themselves" | not built, and deliberately so |

Say which one it is instead of forcing it into the AppSpec.
